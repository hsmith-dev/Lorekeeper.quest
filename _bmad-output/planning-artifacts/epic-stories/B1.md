# Batch B1: E0a, E0-QA, E0-Access

Each story uses the template format, followed by `Status`, `Covers` (requirement ids), `Technical notes` (files and AD refs), `Dependencies` and `Size`. Paths are relative to `src/backend/` (backend) or `src/frontend/src/` (frontend) unless they start with `.github/`, `scripts/`, `docs/`, `licenses/`, `seeds/` or `nginx/`, which are relative to the repo root.

Stories marked **Done** shipped on `main` and are kept so that their ids stay stable and the coverage map can be checked. A dev agent should not pick them up.

**Standing ACs** (epics-parallel-plan §1) apply to every open story they fit and are not repeated in each story:

- **Route:** a new or changed route has an EV-4 probe in `tests/ev4/probes/<feature>.py` or a reasoned exemption. Hidden, forbidden and missing records all return `404 {"detail":"Not found"}`. AI and streaming routes also get `@limiter.limit` keyed `user_or_ip`, plus a `nginx/locations.conf` line.
- **Dependency:** a new dependency gets a `licenses/register.yaml` line in the same story.
- **Migration:** a schema change ships as an Alembic revision, rebased onto head, and every new or changed model is registered in `access/registry.py`.

## Decisions

- **B1-D1 Shipped work is kept as Done stories.** E0a.1 (PR #1), E0-QA.1 and E0-QA.2 (PR #2) and E0-QA.3 (PR #4, D-7 resolved: only `pages.yml`) keep their ids so the coverage map stays checkable. Their remaining gaps are separate open stories: path filters, the register, image scanning and owner confirmation.
- **B1-D2 Test DB variable name.** The env var is `TEST_DATABASE_URL`, the AD-21 and parallel-plan contract. The module constant `TEST_DB_URL` stays and reads from it, so it is env-overridable as asked without breaking imports. A `_test` suffix guard protects real databases.
- **B1-D3 Share-link expiry is not in E0a.** It needs `campaign_share_tokens.expires_at` from F1-core, and E0a must ship alone and first. Expiry is enforced in E0-Access.4 (resolution) and offered in E0-Access.12 (UI), for both kinds of link (AD-12 adds the column to all tokens).
- **B1-D4 Legacy `npcs` and `quests` are `always_gm` from F1-core until F3-world.** Their copies start `visibility=gm` (FR-5, AD-18), and existing Members become Players. Exposing them before the GM publishes would be the opposite of privacy-first. Consequence: read-only links and Players see no NPC or Quest list from the E0-Access release until the GM publishes Entities. Release notes must say so (PRD FR-5 assumption). If the owner prefers continuity, the alternative is a `visibility` column on `npcs`/`quests` defaulting to `party` in F1-core, copied by F3. This is flagged for owner review.
- **B1-D5 `party_embedding` is filled without Jobs.** E0-Jobs comes after E0-Access in the DAG, so E0-Access.7 computes `party_embedding` inline on save (failure leaves NULL and never blocks the save) and ships an idempotent backfill script. Non-GM vector search skips NULL rows rather than falling back to the Shorthand-bearing `embedding`. E0-Journal later folds this into `reindex_entry` and `journal.reembed`.
- **B1-D6 Bulk Visibility route.** E0-Access.9 adds `POST /api/campaigns/{id}/visibility` in a new `api/routes/visibility.py` (E0-Access-owned), because E7 needs a backend for bulk controls and the spine names only the function. E7 consumes it and does not define its own.
- **B1-D7 `access:` channel versus "exactly three channels".** AD-13 requires publishing `access:{campaign_id}:{grant_id}`, while AD-5 says `core/pubsub.py` has exactly three channels. These stories treat `access:` as an access-control channel published only by `app/access/` (not a `core/pubsub` feature channel), so both rules hold.
- **B1-D8 SSE before B2's helpers exist.** E0-Access.11 writes its own minimal SSE framing and keeps its stream reader inside `useCampaignEvents.ts`, because `core/sse.py` and `lib/sse.ts` belong to E0-Jobs, which comes later. E0-Jobs swaps them in. `grant_watch` (E0-Access.10) is the close signal B2's `sse_response` must call.
- **B1-D9 Captured-context probes depend on E0-LLM.** The EV-4 hard gate (E0-QA.14) needs E0-LLM's capture hook. E0-LLM is a parallel Wave 0 epic, not a later one, so this dependency is allowed. Until the hook lands, the chat probes run response-side checks and the gate stays red, by design.
- **B1-D10 CUDA wheels are `pending`, not exceptions.** The NVIDIA wheels in the shipped backend image are tracked as pending items that warn, tied to E0-Platform's AD-1 refactor, so `main` doesn't go red on a known issue while new packages still fail. Redistributing a GPU image under the NVIDIA EULA is recorded as an open owner decision in `docs/LICENSING.md`.
- **B1-D11 More stories than estimated.** E0-Access has 13 stories (estimate 8) and E0-QA has 15 (estimate 7, of which 3 are Done), so that each one fits a single dev session. The FR-9(b) release rule is unaffected: E0-Access is still released as one unit.
- **B1-D12 Seams for later epics, not dependencies on them.** `set_visibility` exposes `register_stale_marker` (E0-Jobs: `derived_sources`), `register_visibility_listener` (E0-Journal: the `visibility_changed` hook) and a registry `writer` slot (E0-WorldCore: `apply_change`). Each later epic registers into these. None of the B1 stories depends forward.
